Week 15: Capstone — Ship a Production FastAPI Service

There's no new syntax this week. You're picking a real project — an issue tracker, a booking system, or an inventory service — and building it to the standard every earlier week set: typed and validated endpoints, real auth, a layered test suite, structured logs and health checks, a non-root container, and a deploy a stranger could actually reach. The hard part of a capstone is almost never the code; it's resisting the urge to build fifteen resources instead of doing three resources properly, all the way through to a deployed URL.

Module 12 of 12 Week 15 of 15 ~8–12 Hours Capstone Project

By the end of this week, you'll be able to

  • Scope a real service and sketch its resource model and API contract before writing implementation code
  • Secure the service with real auth, and back it with a unit, integration and API-level test suite
  • Containerize, deploy and document the service well enough that a stranger can run and verify it

1. Plan a Coherent Service & API Contract

Pick one project and commit to it: an issue tracker (projects, issues, comments, status transitions), a booking system (resources, time slots, reservations, cancellation rules), or an inventory service (products, warehouses, stock movements, low-stock alerts) all give you enough surface area to demonstrate everything from Weeks 2–13 without needing to invent scope. Any of the three works equally well as a portfolio piece — what matters is depth on one of them, not breadth across all three.

Before writing a single Pydantic model, sketch the resource model and the endpoints that operate on it. What are the nouns? What relationships exist between them (an issue belongs to a project; a comment belongs to an issue)? What state transitions are legal (an issue moves from open to in_progress to closed, but not directly from closed back to open without a reason)? Writing this down as a short table — resource, endpoint, method, auth requirement, status codes — forces the ambiguous decisions to happen on paper, where they're cheap to change, instead of three files deep into an implementation where they're expensive to unwind.

issue-tracker-contract.md
Resource: Project (owner_id, name, slug)
Resource: Issue   (project_id, title, status, assignee_id, created_by)
Resource: Comment (issue_id, author_id, body)

POST   /projects                     auth: any user          -> 201
GET    /projects/{id}                auth: member of project -> 200 | 404
POST   /projects/{id}/issues         auth: member of project -> 201
GET    /projects/{id}/issues         auth: member of project -> 200
PATCH  /issues/{id}/status           auth: assignee or owner -> 200 | 409 (illegal transition)
POST   /issues/{id}/comments         auth: member of project -> 201
GET    /healthz                      auth: none               -> 200

Over-scoping is the single most common way capstones fail — not technical difficulty, but running out of the week partway through a sprawling schema with no tests, no auth, and nothing deployed. A tightly scoped service with three resources, real authorization, a real test suite, and a working deployment is a dramatically stronger portfolio piece than ten resources with none of that. Decide upfront what's explicitly out of scope — real-time notifications, file uploads, a full permissions matrix — and write that decision into your README rather than discovering it by running out of time.

2. Secure, Test & Observe the System

Apply Weeks 6–7 for real: every write endpoint should require authentication via the OAuth2 password flow and JWTs, and authorization should be enforced with dependencies that check ownership or membership, not just "is logged in." In the issue tracker example, a user should only be able to change the status of an issue in a project they belong to — that check belongs in a reusable dependency, not duplicated across every route that touches issues.

deps.py
async def require_project_member(
    project_id: int,
    current_user: User = Depends(get_current_user),
    db: AsyncSession = Depends(get_db),
) -> User:
    is_member = await memberships.exists(db, project_id, current_user.id)
    if not is_member:
        raise HTTPException(status_code=403, detail="Not a member of this project")
    return current_user

Back it with the layered suite from Week 8: unit tests for pure business logic (is this status transition legal?) that need no database at all, integration tests against a real test database via Testcontainers for your repository layer, and API-level tests through TestClient that exercise the full HTTP stack — auth, validation, and response shape together. A capstone with only one of these layers is missing the failure modes the others exist to catch: unit tests alone miss broken SQL; API tests alone are too slow and coarse to pin down which layer regressed.

Then wire in Week 11 and Week 12's observability practices: structured JSON logs that include a request ID so a single request's log lines can be traced through the system, a /healthz endpoint that checks the database connection (not just "the process is alive"), and a handful of prometheus-client metrics — request count, request duration, and something domain-specific like issues created per hour. None of this is decoration; it's the difference between finding out a deployed instance is broken because a user complained, versus finding out because a health check failed.

Test the rejection paths, not just the happy path

A reviewer skimming your test suite will notice immediately if every test asserts a 200 or 201. Deliberately test that an unauthenticated request gets a 401, that a non-member gets a 403, that an illegal status transition gets a 409, and that a malformed request body gets a 422 — these are the tests that demonstrate you actually understood the contract you designed in Topic 1, not just the happy path through it.

3. Containerize, Deploy & Document It

Apply Week 13's Docker approach directly: a multi-stage build that installs dependencies in a builder stage and copies only the resulting virtual environment into a slim runtime image, running as a non-root user, with migrations run as an explicit release step rather than on every worker's startup. Wire a minimal CI pipeline — even just "install dependencies, run the test suite, build the image" on every push — so the deployed image is provably the one that passed your tests, not whatever happened to be on your laptop.

.github/workflows/ci.yml
name: CI
on: [push]
jobs:
  test-and-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install poetry && poetry install
      - run: poetry run pytest
      - run: docker build -t capstone-service .

Deploy the image somewhere a link can actually reach — a free tier on Fly.io, Render, or Railway is enough; the point isn't the hosting bill, it's proving the container runs correctly outside your own machine, with real environment variables and a real (even small) managed database instead of localhost. Then write the README a stranger — a recruiter, an interviewer, a future teammate — actually needs: what the service does and why you scoped it the way you did, how to run it locally and run the test suite, which environment variables it needs and where to get test values for them, and the deployed URL with a couple of example requests they can run immediately without reading your source code first.

Document decisions, not just commands

A README that's only setup commands tells a reviewer nothing about your judgment. Add a short "design decisions" section: why you chose this scope, what you deliberately left out and why, and one tradeoff you'd revisit with more time. That's the section that actually differentiates a capstone in a portfolio review.

4. Hands-on Exercise

Capstone

Build and deploy a portfolio-grade FastAPI service

Pick issue tracking, bookings, or inventory (or a comparable scope you can justify), and apply every module from this course to it. This is a definition-of-done checklist, not a suggestion list — treat every item as required for the capstone to count as complete.

Definition of done:

  1. A documented resource model and API contract exist before implementation, with an explicit "out of scope" note for anything you deliberately excluded.
  2. Database migrations exist for the full schema, and a seed script can populate a fresh database with realistic sample data.
  3. Every write endpoint requires authentication, and authorization is enforced by ownership or membership checks — not just "is any user logged in."
  4. A layered test suite exists: unit tests for business logic, integration tests against a real test database, and API-level tests through TestClient, including deliberate tests of 401/403/409/422 rejection paths.
  5. The service emits structured logs with a request ID, exposes a /healthz endpoint that checks real dependencies, and reports at least a handful of Prometheus metrics.
  6. A multi-stage, non-root Docker image builds in CI, with the test suite gating the build so a broken build can never reach the image step.
  7. The service is deployed to a real (free-tier is fine) host at a URL that's actually reachable, backed by a real managed database rather than an in-memory or SQLite fallback.
  8. A README documents setup, environment variables, how to run the test suite, the deployed URL with example requests, and the architectural decisions behind your scope.
Hint

Work top to bottom through this checklist in order, and get item 7 — an actual deployed URL — done earlier than feels natural, even with a half-finished feature set. A service that's deployed early and grown incrementally almost always ends the week in better shape than one where deployment was saved for "once everything's ready," because deployment surfaces environment and configuration problems you want to find on day one, not day six.

5. Knowledge Check

Four reflective questions — there's no single correct answer, but a strong capstone submission should be able to defend its position on each.

Q1

What makes a project production-ready rather than merely feature-complete?

Feature-complete means the happy path through every endpoint works when you try it yourself. Production-ready means it has the operational qualities that let it survive contact with real, unpredictable use: security that actually restricts who can do what, a test suite that catches regressions before users do, deliberate handling of failure and rejection paths (not just success), observability that tells you something's wrong before a user reports it, a repeatable deployment process, and documentation that lets someone other than you operate it. A demo can be feature-complete in an afternoon; production-readiness is what the rest of this course was actually teaching.

Q2

How should you decide the scope of your capstone so it's realistically finishable in the time available?

Pick the smallest set of resources that still lets you demonstrate a real relationship and a real state transition — not "how many resources can I fit," but "what's the minimum surface area that isn't trivial." An issue tracker with just projects and issues, done with real auth, full test coverage, and a deployment, beats an issue tracker with projects, issues, comments, labels, notifications, and attachments where only the first two are actually finished. Write down what's out of scope explicitly and early, rather than discovering the cutoff by running out of time on the last day.

Q3

Why is a single "it works on my machine" pytest run insufficient evidence that the service is ready to ship?

It only proves the code works against whatever database, environment variables, and dependency versions happen to be installed on your machine right now — none of which are guaranteed to match production. A test suite that only ever runs locally also doesn't prove anything about the next change someone makes; without CI enforcing it on every push, a passing suite today says nothing about whether the version you actually deploy tomorrow still passes. Running the same tests in a clean CI environment against a containerized database, and gating the Docker build on them passing, is what turns "it worked when I ran it" into an actual guarantee about what ships.

Q4

Who is the real audience for your capstone README, and what should it let them do without asking you anything?

A stranger with no prior context — a recruiter skimming your portfolio, an interviewer preparing questions, or a future teammate onboarding onto the project. That README should let them clone the repository, set up the required environment variables, run it locally, run the test suite, and hit the deployed URL with example requests, all without messaging you first. It should also explain the scope decisions behind the project, since a reviewer who understands why you built it the way you did learns more about your judgment than one who only sees the endpoints.

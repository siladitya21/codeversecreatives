Week 17: gRPC & Protocol Buffers for Service-to-Service Calls

Every service-to-service call this course has made — Week 9's async patterns aside — has assumed plain JSON over REST. That's the right default when a browser or a third party is the caller; it's not the only option once two of your own services are talking to each other and you control both ends. This week introduces gRPC: a binary, strongly-typed RPC framework built on HTTP/2 and Protocol Buffers, widely used for internal service-to-service traffic where REST's flexibility isn't needed and its overhead genuinely costs something.

1. Defining a Contract with Protocol Buffers

Where a REST API's contract lives in Zod schemas and (loosely) in OpenAPI docs, a gRPC service's contract is a .proto file — a language-neutral schema that generates strongly-typed client and server code for TypeScript, Go, Java, or any other supported language from the exact same source of truth.

proto/inventory.proto
syntax = "proto3";

package inventory;

service InventoryService {
  rpc ReserveStock (ReserveRequest) returns (ReserveResponse);
}

message ReserveRequest {
  string sku = 1;
  int32 quantity = 2;
}

message ReserveResponse {
  string reservationId = 1;
  bool success = 2;
}

The numbers after each field (= 1, = 2) aren't default values — they're each field's unique position in the message's binary wire format, which is how Protocol Buffers achieves both a compact binary encoding and safe schema evolution: a new field can be added with a new number without breaking old clients that don't know about it, as long as existing field numbers are never reused or renumbered.

terminal — generating TypeScript types from the .proto file
npx ts-proto \
  --ts_proto_out=./src/generated \
  --ts_proto_opt=nestJs=false \
  -I proto proto/inventory.proto

# generates src/generated/inventory.ts with typed
# message interfaces and a service client/server definition
Never reuse or renumber a field's tag once it's shipped

The field number, not the field name, is what's actually encoded on the wire. Renumbering an existing field, or reusing a number a now-deleted field once had, makes an old message unparseable or silently misinterpreted by a client still expecting the original meaning. Deprecate a field by marking it reserved in the schema instead of ever reusing its number.

2. A gRPC Server & Client in Node

@grpc/grpc-js is the official, pure-JavaScript gRPC implementation for Node. Combined with the generated types from Section 1, it gives you a server implementation and client calls that look like ordinary async functions, with real typed request/response objects instead of untyped JSON.

src/grpc/server.ts
import * as grpc from "@grpc/grpc-js";
import { InventoryServiceService, ReserveRequest, ReserveResponse } from "../generated/inventory.js";

async function reserveStock(
  call: grpc.ServerUnaryCall<ReserveRequest, ReserveResponse>,
  callback: grpc.sendUnaryData<ReserveResponse>
) {
  const { sku, quantity } = call.request;

  if (!(await hasStock(sku, quantity))) {
    callback({
      code: grpc.status.FAILED_PRECONDITION,
      message: `Insufficient stock for ${sku}`,
    });
    return;
  }

  const reservationId = await createReservation(sku, quantity);
  callback(null, { reservationId, success: true });
}

const server = new grpc.Server();
server.addService(InventoryServiceService, { reserveStock });
server.bindAsync("0.0.0.0:50051", grpc.ServerCredentials.createInsecure(), () => {
  server.start();
  console.log("gRPC server listening on 50051");
});
src/grpc/client.ts — called from another Node service
import * as grpc from "@grpc/grpc-js";
import { InventoryServiceClient } from "../generated/inventory.js";

const client = new InventoryServiceClient(
  "inventory-service:50051",
  grpc.credentials.createInsecure()
);

const response = await new Promise<ReserveResponse>((resolve, reject) => {
  client.reserveStock({ sku: "ABC123", quantity: 2 }, (err, res) => {
    if (err) reject(err);
    else resolve(res!);
  });
});

Notice there's no manual JSON serialization, no URL string to get right, and no response schema to validate by hand — call.request.sku and response.reservationId are typed properties generated directly from the .proto file, and a typo in a field name is a TypeScript compile error caught immediately, not a silently-wrong object key discovered at runtime.

Use gRPC's own status codes, not a made-up error convention

gRPC has its own standard status code set (NOT_FOUND, FAILED_PRECONDITION, UNAUTHENTICATED, and others) analogous to HTTP status codes — use them via the callback's error argument rather than inventing a custom error field inside your response message. Clients and tooling across every language already know how to handle standard gRPC status codes correctly.

3. Streaming RPCs & gRPC vs. REST

Beyond the simple request-response call from Section 2, gRPC supports streaming natively, built on HTTP/2's ability to multiplex multiple streams over one connection — a real alternative to Week 9–10's WebSocket work for service-to-service (not browser-facing) real-time data.

proto/inventory.proto — a server-streaming RPC
service InventoryService {
  rpc WatchStockLevel (WatchRequest) returns (stream StockUpdate);
}

message WatchRequest { string sku = 1; }
message StockUpdate { string sku = 1; int32 quantity = 2; }
server.ts — writing a stream of updates
function watchStockLevel(call: grpc.ServerWritableStream<WatchRequest, StockUpdate>) {
  const unsubscribe = onStockChange(call.request.sku, (quantity) => {
    call.write({ sku: call.request.sku, quantity });
  });

  call.on("cancelled", unsubscribe);   // client disconnected -- clean up
}

A client consuming watchStockLevel receives each StockUpdate as it's written, over the same long-lived connection, rather than polling a REST endpoint repeatedly or standing up a separate WebSocket server for the same purpose.

None of this makes gRPC a universal replacement for REST. REST's plain-text JSON is trivially debuggable with curl and readable in a browser network tab; gRPC's binary wire format needs dedicated tooling (grpcurl, a gRPC-aware client) to inspect. Browsers can't call a gRPC service directly without a proxy layer (gRPC-Web), which makes REST the natural choice for anything a browser or a public, loosely-coupled third party talks to directly — exactly the traffic your Week 3 REST API and Week 9–10 WebSockets already handle. gRPC earns its place specifically for internal, service-to-service traffic you control on both ends.

A hybrid architecture is normal, not a compromise

A real system commonly runs REST (and WebSockets, for browser real-time) at its public edge — where browsers, mobile apps, and third parties connect — and gRPC for the internal service-to-service mesh behind that edge, where you control both ends and the traffic volume justifies the added tooling. Choosing one for the whole system by default, rather than per-boundary, is usually the wrong call either direction.

5. Knowledge Check

Three quick questions. Expand each to check your answer.

Q1

Why must a Protocol Buffers field's number never be reused after that field is removed?

The field number, not its name, is what's actually encoded in the binary wire format. If a new field reuses a number a deleted field once had, an old message serialized under the original schema (or a client still running the old schema) can be misinterpreted as containing the new field's data, silently corrupting the value rather than failing loudly.

Q2

Why is a browser generally unable to call a gRPC service directly, unlike a REST API?

gRPC relies on HTTP/2 trailers and framing details that browsers' fetch/XHR APIs don't fully expose, and its binary Protocol Buffers payloads aren't natively readable the way JSON is. A browser client needs a proxy layer (gRPC-Web) translating between what the browser can actually send and a real gRPC connection — REST's plain HTTP and JSON need no such translation layer.

Q3

What kind of traffic is gRPC the strongest fit for, versus where REST or WebSockets remain the better default?

gRPC fits internal, service-to-service traffic where you control both ends and the volume justifies its binary serialization performance and native streaming support. REST and WebSockets remain the better default at a system's public edge — anything a browser, mobile app, or loosely-coupled third party talks to directly — where plain-text JSON's universal tooling and debuggability matter more than raw efficiency.

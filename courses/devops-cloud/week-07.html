Week 7: Deployment Strategies & Environments

Last week's pipeline pushes a scanned image to a registry the moment code lands on main — but pushing an image and putting it in front of real users are two different acts, and conflating them is how an untested change reaches production at 2 a.m. This week adds the missing layer: GitHub Environments that gate a deploy behind a human approval, the rolling, blue-green and canary strategies for actually rolling that image out, and a rollback plan for when the rollout goes wrong. The environment gates you set up here are what plug directly into the EC2 and S3 targets you provision in Week 8, and canary-style traffic shifting reappears almost unchanged as a Kubernetes rolling update in Week 12.

Module 5 of 22 Week 7 of 26 ~3–4 Hours Hands-on Exercise Included

By the end of this week, you'll be able to

  • Configure a GitHub Environment with required reviewers to gate a production deploy
  • Explain the tradeoffs between rolling, blue-green and canary deployment strategies
  • Design a rollback plan that gets a failed deploy back to a known-good state quickly

1. GitHub Environments & Approvals

A GitHub Environment (Settings > Environments) is a named deployment target — staging, production — that a job can declare with environment:. Environments carry their own scoped secrets and, more importantly, protection rules: required reviewers who must manually approve a run before it proceeds, and optional wait timers or branch restrictions.

.github/workflows/deploy.yml
name: Deploy

on:
  workflow_run:
    workflows: ["Build, Test & Push"]
    types: [completed]
    branches: [main]

jobs:
  deploy-staging:
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - name: Deploy to staging
        run: ./scripts/deploy.sh staging ${{ github.event.workflow_run.head_sha }}

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production   # protection rule: 1 required reviewer, configured in repo settings
    steps:
      - name: Deploy to production
        run: ./scripts/deploy.sh production ${{ github.event.workflow_run.head_sha }}

When deploy-production reaches the environment: production line, GitHub pauses the run and waits — a designated reviewer sees a notification, opens the run, and clicks Approve or Reject before a single deploy command executes. Nothing about the workflow YAML enforces this; the protection rule lives in the environment's settings, so the same job definition can run unattended against staging and require a human sign-off against production.

Deploy through staging first, always

Structuring deploy-production with needs: deploy-staging means production can never receive a build that staging hasn't already run — the approval gate is a second check, not the only check. Skipping straight to production "just this once" is how the one untested edge case finds real users.

2. Deployment Strategies: Rolling, Blue-Green, Canary

Once a deploy is approved, how the new version actually replaces the old one on live traffic is a separate decision, with real tradeoffs between simplicity, cost, and blast radius if something's wrong.

Rolling deployment replaces instances a few at a time — take one old instance out of the load balancer, start a new one, health-check it, add it back, repeat. No extra infrastructure is needed since you're reusing the same fleet, but a bad deploy is live on part of your traffic the moment the first instance rolls, and a full rollback means rolling every instance back the same way.

terminal — conceptual rolling update
# Simplified view of what a rolling deploy does across a 4-instance fleet
for instance in i-01 i-02 i-03 i-04; do
  drain_from_load_balancer "$instance"
  deploy_new_version "$instance"
  wait_for_healthy "$instance"
  add_to_load_balancer "$instance"
done

Blue-green deployment runs two complete, identical environments — "blue" (currently live) and "green" (the new version) — side by side. Traffic switches all at once, usually at the load balancer or DNS layer, once green passes health checks. Rollback is nearly instant: point traffic back at blue. The cost is running double the infrastructure, even if only briefly, and any database schema change has to stay compatible with both versions during the switch.

Canary deployment sends a small percentage of real traffic — say 5% — to the new version while the rest keeps hitting the old one, then gradually increases that percentage while watching error rates and latency. It catches problems that only show up under real production traffic patterns, with the smallest possible blast radius, but needs traffic-splitting infrastructure (a service mesh, a smart load balancer, or a platform like Kubernetes) and active monitoring to be worth the added complexity.

terminal — conceptual canary rollout with a load balancer weight
set_traffic_weight --version=new --percent=5
watch_error_rate --version=new --duration=10m   # abort and roll back on any spike

set_traffic_weight --version=new --percent=25
watch_error_rate --version=new --duration=10m

set_traffic_weight --version=new --percent=100  # fully promoted
Pick the strategy to match the risk, not the hype

A low-traffic internal tool rarely justifies canary's added complexity — a rolling deploy with good health checks is plenty. Reserve blue-green and canary for services where a bad deploy under real traffic is expensive: customer-facing payment flows, high-traffic APIs, anything where "we'll just watch it closely" isn't a real safety net.

3. Rollback Strategy

A rollback plan you design in advance is fast; one you improvise during an incident is slow and error-prone. The baseline requirement, from Week 5's tagging discipline, is that every deployed artifact is addressable by an immutable tag — "roll back" should always mean "redeploy the previous known-good SHA," never "try to remember what we had before."

.github/workflows/rollback.yml
name: Rollback

on:
  workflow_dispatch:
    inputs:
      sha:
        description: "Git SHA of the known-good image to redeploy"
        required: true

jobs:
  rollback:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Redeploy known-good image
        run: ./scripts/deploy.sh production ${{ github.event.inputs.sha }}

workflow_dispatch with an input gives you a manual "Run workflow" button in the GitHub UI where you paste in the last good SHA — deliberately simple, because during an active incident is the worst time to be debugging a complicated automated rollback system. The environment protection rule still applies, but under incident conditions the on-call engineer is usually also the approver.

Each strategy rolls back differently: blue-green just flips traffic back to the still-running old environment (fastest); rolling has to roll every instance back through the same drain-deploy-health-check cycle it used going forward (slower, same mechanism in reverse); canary simply sets the new version's traffic weight back to zero, since the old version never stopped serving the majority of traffic. Whatever the mechanism, a rollback should never depend on a database migration being reversible on demand — that has to be designed in ahead of time, by keeping schema changes backward-compatible for at least one deploy cycle.

Practice the rollback before you need it

A rollback workflow nobody has ever run is a rollback workflow you can't trust during an actual incident. Run it against staging on a normal Tuesday — confirm the button exists, the right person has access, and the deploy script actually accepts a specific SHA — so the first time it runs for real isn't also the first time anyone's seen it work.

4. Hands-on Exercise

Hands-on

Gate a deploy behind staging and an approval

Extend last week's build-test-push pipeline with real environment gating and a documented deployment strategy.

Requirements:

  1. In your repository, create two Environments: staging (no protection rules) and production (add yourself as a required reviewer).
  2. Add a deploy.yml workflow triggered by workflow_run on your build-test-push workflow's completion, with a deploy-staging job using environment: staging.
  3. Add a deploy-production job with needs: deploy-staging and environment: production, using a placeholder deploy script (e.g. echo "Deploying $IMAGE_TAG to production").
  4. Push a commit to main and confirm in the Actions tab that deploy-production pauses waiting for your approval, then approve it and watch it complete.
  5. Write a one-paragraph deployment strategy decision for a hypothetical checkout service: choose rolling, blue-green, or canary, and justify it against the tradeoffs from section 2.
  6. Add a rollback.yml workflow using workflow_dispatch with a required sha input, gated by the same production environment.
Hint

You don't need real infrastructure to practice this — a placeholder script that echoes what it would do is enough to prove out the environment gating and approval flow. The real deploy target arrives in Week 8 once you have an actual EC2 instance or S3 bucket to point at.

5. Knowledge Check

Four quick questions. Expand each to check your answer.

Q1

What actually enforces a required-reviewer approval — the workflow YAML or something else?

The protection rule lives in the Environment's settings in the repository, not in the workflow file itself. A job simply declares environment: production, and GitHub pauses that job when it reaches that line, checking the environment's configured protection rules — which is why the same job definition can run straight through against staging and pause for approval against production.

Q2

Why is blue-green's rollback faster than a rolling deployment's rollback?

Blue-green keeps the old environment fully running and idle after the switch, so rollback is just flipping the traffic router back to it — a near-instant change. A rolling deployment has already replaced instances in place, so rolling back means running the same drain-deploy-health-check cycle again in reverse across every instance, which takes roughly as long as the original rollout did.

Q3

Why would a low-traffic internal tool not need a canary deployment strategy?

Canary's value comes from catching problems under real production traffic with a small blast radius, but it needs traffic-splitting infrastructure and active monitoring to actually deliver that. On a low-traffic internal tool, the risk of a bad deploy is already small and cheap to notice and fix, so the added operational complexity of canary usually isn't worth it — a rolling deploy with a solid health check is enough.

Q4

Why should a rollback plan never rely on reversing a database migration on the fly?

A schema migration can be destructive or hard to reverse cleanly once new data has been written under the new schema, so "just undo the migration" during an incident is often unsafe or outright impossible. The reliable approach is designing migrations to be backward-compatible for at least one deploy cycle, so rolling the application code back to the previous version still works against the current schema without needing to touch the database at all.

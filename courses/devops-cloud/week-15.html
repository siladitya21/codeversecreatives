Week 15: Capstone — Ship a Full CI/CD → Cloud Pipeline

This is the final week — no new tools, just everything from Weeks 1–14 wired together into one working system. You'll provision real AWS infrastructure with Terraform, build a GitHub Actions pipeline that tests, scans and pushes a container image, deploy it to a Kubernetes cluster running on that infrastructure, and layer on the observability and security practices from the last two modules — a complete path from git push to a running service in the cloud, and a portfolio-ready project you can walk an interviewer through end to end.

Module 12 of 12 Week 15 of 15 ~10–15 Hours Capstone Project

By the end of this capstone, you'll be able to

  • Provision a VPC, compute and a container registry on AWS entirely through versioned Terraform
  • Build a GitHub Actions pipeline that tests, scans, builds and deploys a containerized app to Kubernetes on every push
  • Explain and defend every architectural decision in the pipeline, from state locking to rollout strategy

1. Project Planning & Architecture

Before touching Terraform or YAML, write down what you're actually deploying and where. Reuse a small containerized app you already have from earlier in this course — a health-check API, a small CRUD service, anything with a Dockerfile and a /healthz endpoint is enough. The architecture doesn't need to be ambitious to be a strong capstone; it needs to be complete and correctly reasoned:

  • Compute target — a single-node k3s cluster running on one EC2 instance is the realistic choice for a free-tier capstone: it's genuinely Kubernetes (the same manifests, the same kubectl), without the ongoing cost of a managed EKS control plane. Note in your write-up that a production system would likely use EKS instead, and why (managed control plane, multi-AZ node groups) — understanding the tradeoff matters more than which one you provision here.
  • Registry — a private AWS ECR repository, matching Week 5.
  • Networking — one VPC with a public subnet for the instance, matching Week 8, with a security group open only on the ports the pipeline and cluster actually need (22 for SSH during setup, 6443 for the Kubernetes API, 80/443 for the app).

Sketch the full path a change takes before writing any code: a push to main triggers CI, which tests and scans the app, builds and pushes an image to ECR, then tells the cluster to roll out that new image. Write that sequence down as a short numbered list — it becomes both your pipeline's job order in Section 3 and the architecture diagram in your final write-up.

2. Provisioning Infrastructure with Terraform

Everything below is real infrastructure, provisioned the Week 9–10 way: written as HCL, planned before it's applied, and backed by remote state from the start so a second contributor (or future you, from a different machine) can safely run terraform plan against the same state.

backend.tf — remote state, provisioned once by hand
terraform {
  backend "s3" {
    bucket         = "codeverse-capstone-tfstate"
    key            = "capstone/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}
main.tf — VPC, EC2 instance & ECR repository
provider "aws" {
  region = "us-east-1"
}

resource "aws_vpc" "capstone" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  tags = { Name = "capstone-vpc" }
}

resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.capstone.id
  cidr_block              = "10.0.1.0/24"
  map_public_ip_on_launch = true
  tags = { Name = "capstone-public" }
}

resource "aws_internet_gateway" "gw" {
  vpc_id = aws_vpc.capstone.id
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.capstone.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.gw.id
  }
}

resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id
  route_table_id = aws_route_table.public.id
}

resource "aws_security_group" "cluster" {
  name   = "capstone-cluster-sg"
  vpc_id = aws_vpc.capstone.id

  ingress { from_port = 22   to_port = 22   protocol = "tcp" cidr_blocks = [var.admin_cidr] }
  ingress { from_port = 6443 to_port = 6443 protocol = "tcp" cidr_blocks = [var.admin_cidr] }
  ingress { from_port = 80   to_port = 80   protocol = "tcp" cidr_blocks = ["0.0.0.0/0"] }
  ingress { from_port = 443  to_port = 443  protocol = "tcp" cidr_blocks = ["0.0.0.0/0"] }
  egress  { from_port = 0    to_port = 0    protocol = "-1"  cidr_blocks = ["0.0.0.0/0"] }
}

resource "aws_instance" "k3s_node" {
  ami                    = "ami-0c101f26f147fa7fd" # Ubuntu 22.04 LTS, us-east-1
  instance_type          = "t3.small"
  subnet_id              = aws_subnet.public.id
  vpc_security_group_ids = [aws_security_group.cluster.id]
  key_name                    = var.key_pair_name
  associate_public_ip_address = true

  user_data = file("${path.module}/install-k3s.sh")

  tags = { Name = "capstone-k3s-node" }
}

resource "aws_ecr_repository" "app" {
  name                 = "capstone-app"
  image_tag_mutability = "IMMUTABLE"
  image_scanning_configuration {
    scan_on_push = true
  }
}

output "node_public_ip" {
  value = aws_instance.k3s_node.public_ip
}

image_tag_mutability = "IMMUTABLE" matters more than it looks: it rejects pushing a second image under a tag that already exists in the repository, which forecloses an entire class of "which image is actually running?" incidents — every tag in this repo, once pushed, unambiguously refers to one exact image forever. scan_on_push wires Week 5's image scanning directly into the registry itself, not just into CI, so nothing that reaches ECR skips a scan regardless of how it got there.

terminal — the plan/apply loop from Week 9
terraform init
terraform plan -out=tfplan
terraform apply tfplan

# get the node's IP for the next section
terraform output node_public_ip
Never skip the remote backend, even for a capstone

It's tempting to leave state local for a "just for me" project — but wiring up S3 + DynamoDB locking from the start, per Week 10, is what proves you can build infrastructure a team could actually collaborate on, not just infrastructure that happens to work on one laptop. It's also the difference that matters most if your laptop dies mid-capstone and you need to pick the project back up from a different machine.

3. The CI/CD Pipeline

With infrastructure in place, the pipeline is where Weeks 3 through 7 converge: test and scan the app, build and push an image, then trigger a deploy — each stage gated on the previous one succeeding, exactly like Week 7's environments-and-approvals model.

.github/workflows/deploy.yml
name: Build, Scan & Deploy

on:
  push:
    branches: [main]

env:
  ECR_REPOSITORY: capstone-app
  AWS_REGION: us-east-1

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./run-tests.sh   # your app's own test suite from earlier weeks

  build-scan-push:
    needs: test
    runs-on: ubuntu-latest
    outputs:
      image: ${{ steps.image.outputs.image }}
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_DEPLOY_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}
      - uses: aws-actions/amazon-ecr-login@v2
        id: ecr-login

      - name: Build image
        run: docker build -t ${{ steps.ecr-login.outputs.registry }}/${{ env.ECR_REPOSITORY }}:${{ github.sha }} .

      - name: Scan image
        uses: aquasecurity/trivy-action@0.24.0
        with:
          image-ref: ${{ steps.ecr-login.outputs.registry }}/${{ env.ECR_REPOSITORY }}:${{ github.sha }}
          severity: CRITICAL,HIGH
          exit-code: 1   # fail the job -- a critical CVE never reaches "push"

      - name: Push image
        run: docker push ${{ steps.ecr-login.outputs.registry }}/${{ env.ECR_REPOSITORY }}:${{ github.sha }}
      - id: image
        run: echo "image=${{ steps.ecr-login.outputs.registry }}/${{ env.ECR_REPOSITORY }}:${{ github.sha }}" >> "$GITHUB_OUTPUT"

  deploy:
    needs: build-scan-push
    runs-on: ubuntu-latest
    environment: production   # requires a reviewer approval -- Week 7
    steps:
      - uses: actions/checkout@v4
      - name: Configure kubeconfig
        run: |
          mkdir -p ~/.kube
          echo "${{ secrets.KUBECONFIG_B64 }}" | base64 -d > ~/.kube/config
      - name: Roll out new image
        run: |
          kubectl set image deployment/capstone-app \
            app=${{ needs.build-scan-push.outputs.image }} \
            --record
          kubectl rollout status deployment/capstone-app --timeout=120s

Two things here are worth calling out explicitly, both of them carrying a lesson forward from earlier weeks. First, role-to-assume instead of a long-lived AWS access key pair: the runner assumes a narrowly-scoped IAM role for the duration of the job via OIDC federation and gets no standing credentials at all — the least-privilege principle from Week 8 and Week 14, applied to the pipeline's own AWS access, not just the application's. Second, exit-code: 1 on the Trivy scan step means a critical vulnerability doesn't produce a warning buried in a log — it fails the job and the image never gets pushed, which is the difference between a scan that's a real gate and one that's decoration.

kubectl rollout status after the image update is what makes this pipeline trustworthy: the job doesn't report success the instant it issues the command, it waits and confirms the new pods actually became ready. A deploy that silently ships a crash-looping pod and reports green is worse than one that fails loudly — the whole point of this step is to make sure that can't happen.

4. Deploying to Kubernetes

The manifests being rolled out are the same shapes from Weeks 11–12 — a Deployment for the app's pods, a Service to route traffic to them, and an Ingress to expose it, applied once by hand to bootstrap the cluster before the pipeline in Section 3 takes over updating the image:

k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: capstone-app
spec:
  replicas: 2
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels: { app: capstone-app }
  template:
    metadata:
      labels: { app: capstone-app }
    spec:
      containers:
        - name: app
          image: PLACEHOLDER   # set by `kubectl set image` in the pipeline
          ports:
            - containerPort: 8000
          readinessProbe:
            httpGet: { path: /healthz, port: 8000 }
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet: { path: /healthz, port: 8000 }
            initialDelaySeconds: 15
            periodSeconds: 20
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "500m", memory: "256Mi" }
---
apiVersion: v1
kind: Service
metadata:
  name: capstone-app
spec:
  selector: { app: capstone-app }
  ports:
    - port: 80
      targetPort: 8000

replicas: 2 combined with maxUnavailable: 0 is what makes the rollout in Section 3 a genuinely zero-downtime deploy: Kubernetes must bring up a new, ready pod (maxSurge: 1) before it's allowed to remove an old one, so there is never a moment with fewer than two healthy pods serving traffic. That guarantee only holds because a readinessProbe is defined — without one, Kubernetes considers a pod "ready" the instant its container process starts, which for most apps is well before it can actually serve a request correctly.

Resource requests and limits aren't optional polish on a single-node cluster either: without a request, the scheduler has no information to reason about whether a pod fits on the node at all, and without a limit, one misbehaving pod can starve every other pod on the same node — a much bigger deal on a one-node capstone cluster than it would be on a large multi-node production cluster with room to spread the damage.

5. Observability & Security Pass

A pipeline that deploys correctly but leaves you blind once the app is running only solves half the problem Weeks 13–14 exist to close. Apply both in full, not as an afterthought:

  • Metrics & dashboards — deploy the kube-prometheus-stack Helm chart (Week 12's Helm skill, Week 13's Prometheus/Grafana skill) to scrape both cluster-level metrics and your app's own /metrics endpoint, and build one Grafana dashboard covering request rate, error rate, and pod restarts.
  • Logging — confirm your app logs structured JSON to stdout (Week 13), which kubectl logs and any log-forwarding sidecar can consume without extra parsing.
  • Secrets — every credential the pipeline or the cluster uses (the KUBECONFIG_B64 secret, any app-level API key) lives in GitHub Encrypted Secrets or a Kubernetes Secret, never committed to the repo — verify this with git log -p -- '*.env' '*.pem' turning up nothing.
  • Network policy — add a default-deny NetworkPolicy and one explicit allow rule for the app's actual traffic pattern, so a compromised pod can't freely reach every other pod on the cluster by default.
k8s/network-policy.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-app-ingress
spec:
  podSelector:
    matchLabels: { app: capstone-app }
  policyTypes: [Ingress]
  ingress:
    - from: []
      ports:
        - protocol: TCP
          port: 8000
This section is what separates a demo from a capstone

Getting a container running in Kubernetes is a demo. Getting it there through a tested, scanned, gated pipeline, with dashboards a reviewer can actually look at and a network policy that isn't wide open, is the difference a hiring manager is actually screening for.

6. The Capstone Project

Capstone

Provision, pipeline and ship a real service to the cloud

Take Sections 1–5 fully through to a live, reachable deployment — infrastructure as code, a gated pipeline, and a hardened, observable cluster.

Requirements:

  1. Write and apply the Terraform from Section 2 with a remote S3 + DynamoDB-locked backend, provisioning a VPC, a compute target running Kubernetes, and an ECR repository with scan-on-push enabled.
  2. Bootstrap the cluster with your app's Deployment, Service and Ingress, confirming readiness and liveness probes are both correctly configured against a real endpoint.
  3. Build the GitHub Actions pipeline from Section 3: a test job, a build-scan-push job that fails on a critical vulnerability, and a deploy job gated behind a production environment approval, using short-lived OIDC-assumed AWS credentials rather than a long-lived access key.
  4. Deploy the observability stack from Section 5 and take a screenshot of a working Grafana dashboard showing live traffic from at least one real deploy.
  5. Apply the default-deny NetworkPolicy, confirm secrets are nowhere in git history, and push one real code change through the full pipeline end to end — from commit to a verified zero-downtime rollout.
  6. Write a short README/architecture doc: a diagram of the pipeline and infrastructure, the tradeoffs you made (k3s vs. EKS, single node vs. multi-node), and what you'd change with more time or budget.
Tear it down when you're done

terraform destroy the moment you've captured your screenshots and write-up — an EC2 instance and its associated resources cost real money every hour, and leaving a capstone running indefinitely is the single most common way this project turns into an unpleasant AWS bill.

7. Final Checklist

Before calling the capstone — and the course — done, confirm each of these honestly:

✓

Does every piece of infrastructure exist because Terraform created it, with zero manual console clicks?

A resource created by hand in the AWS console isn't tracked in state, can't be reproduced by terraform apply on a fresh account, and will silently drift out of sync the moment someone edits it outside Terraform. The entire value of Infrastructure as Code depends on terraform plan against a clean checkout producing zero unexpected changes — that's the actual test, not just "the infrastructure works right now."

✓

Does the pipeline fail loudly and stop before deploying if a test fails or a critical vulnerability is found?

A pipeline where deploy can run even after test or the security scan fails isn't actually gating anything — it's cosmetic. The needs: dependency chain and the scanner's non-zero exit code have to be the only path forward; verify this by deliberately breaking a test or referencing an image with a known CVE and confirming the deploy job never starts.

✓

Did a real rollout complete with zero downtime, verified rather than assumed?

Reading the manifest and confirming maxUnavailable: 0 is set is not the same as proving it works — run a small load-generating loop against the service during a real deploy and confirm no requests failed, the same discipline as an integration test proving behavior rather than a code review merely asserting it.

✓

Can every architectural choice — k3s vs. EKS, single node, the specific IAM role scope — be defended in the write-up, not just listed?

Anyone can list "Terraform, GitHub Actions, Kubernetes" as technologies used. A capstone that can explain specifically why k3s on one node was the right call for this project's scope and budget — and what would actually change moving to EKS with real production traffic — demonstrates the judgment a reviewer is screening for, which the tool list alone never does.
